## 💡 프로젝트 개요
**털 한 올**은 2026 간지톤 15팀 출품작으로, 두 가지 방식으로 마음을 돌보는 웹 서비스입니다.

- **마음 돌보기 (혼자):** 홈에서 오늘의 감정을 고르면 AI와의 대화가 시작됩니다. 대화 안에서 그날 필요한 케어 방식(이야기 들어주기 · 위로받기 · 생각 정리하기 · 해볼 행동 찾기)을 고르고, 몇 번 이야기를 나눈 뒤 마무리하면 **나의 양에 털이 한 올** 쌓입니다.
- **고민 목장 (함께):** 고민을 올리면 **털 없는 양 한 마리가 태어나고**, 다른 사용자들의 조언이 털이 되어 그 양이 점점 풍성해집니다. 털이 적은 양이 먼저 보이도록 정렬해 **모든 고민이 조언을 받도록** 했습니다.

두 공간은 털실로 이어집니다. 목장에서 남에게 조언을 보내면 털실이 쌓이고, 그 털실로 나의 양을 꾸밉니다.

**저는 백엔드를 단독으로 맡았습니다.** 11/8~11/10 사흘 동안 53개 커밋, 27개 PR로 MVP를 완성했습니다.

> 기획 단계에서 **"AI 케어는 의학적 진단이나 치료가 아닌 자기 돌봄 도구"** 라고 범위를 명시하고 시작했습니다. 아래 설계는 전부 이 선언을 지키기 위한 것입니다.

## 🛠 사용 기술
- **Backend:** Java 21, Spring Boot 4.1, Spring Data JPA, Spring Security, Bean Validation
- **Database:** MySQL 8.4 (로컬 Docker) / 테스트는 H2(MySQL 모드)
- **LLM:** Upstage Solar Pro 4 · Claude API — `app.llm.provider` 설정으로 **공급자 교체 가능**
- **문서화:** springdoc-openapi (Swagger UI)

## 📌 핵심 설계 — 안전이 먼저인 서비스

마음 건강을 다루는 서비스라 "동작한다"보다 **"위험한 응답이 사용자에게 닿지 않는다"** 가 더 중요하다고 판단했습니다. 백엔드 설계의 절반이 여기에 들어갔습니다.

### 1) 위험도 분류 — 키워드와 LLM의 이중 판정
케어 대화 메시지와 고민 본문은 저장·응답 전에 `RiskClassifier`를 거쳐 `SAFE` / `CAUTION` / `CRISIS`로 분류됩니다.

- **키워드 판정과 LLM 판정 중 더 높은 등급을 채택**합니다. 한쪽이 놓쳐도 다른 쪽이 잡도록 한 구조입니다.
- **이 분류기는 절대 예외를 던지지 않습니다.** LLM이 실패하거나 5초를 넘기면 키워드 결과를 쓰되 **최소 `CAUTION`** 으로 처리합니다. 안전 판정이 서비스 장애로 번지면 안 되고, 동시에 "판정 못 했으니 통과"가 되어서도 안 되기 때문입니다.
- `"방법을 찾는 표현"` 처럼 초기에 놓쳤던 패턴은 실제 테스트에서 발견해 위기로 재분류했습니다.
- 판정 결과는 `crisis_logs`에 남기되 **본문은 제외**하고, 위기 판정 시 상담 연결 배너를 24시간 켭니다.

### 2) AI 응답 안전 가드 — 문장 단위 스트리밍 검사
LLM이 생성한 응답을 그대로 흘려보내지 않고, **문장이 끝날 때마다 금지 패턴을 검사**한 뒤 내보냅니다.

- 차단 대상: **병명 단정, 약 복용·중단 조언, 자해 방법, 의존 유도**
- 걸린 문장은 화면에 내보내지 않고 준비된 안전 문장으로 대체합니다.
- **이미 앞 문장이 나간 뒤 뒷 문장이 걸리는 경우**가 까다로웠습니다. 이때는 `replace` 이벤트로 **말풍선 전체를 안전 문장으로 교체**하도록 설계했습니다. 첫 문장부터 걸리면 교체 없이 안전 문장만 내려갑니다.
- 패턴은 시드 JSON으로 관리해 **재배포 없이 추가**할 수 있고, 1분간 캐시합니다.

### 3) 케어 대화 SSE — 실패까지 설계한 8종 이벤트
`POST /diaries/{id}/care/messages`가 `text/event-stream`으로 응답합니다. 헤더(JWT)를 보내야 해서 `EventSource`가 아니라 **fetch 스트림**으로 읽는 구조입니다.

| 이벤트 | 역할 |
| --- | --- |
| `progress` | 대화 횟수·마무리 가능 여부 (항상 첫 이벤트) |
| `delta` | AI 응답 조각 (안전 가드를 통과한 문장 단위) |
| `crisis` | 위기 판정 시 AI 응답 대신 전환 메시지 |
| `notice` | 응답 지연 재시도 중 ("잠시 숨을 고르고 있어요") |
| `reset` / `replace` | 받은 조각 초기화 / 안전 문장으로 전체 교체 |
| `error` / `done` | 3회 실패 / 정상 종료 |

- 최대 3번까지 재시도하고, **실패해도 사용자가 한 말은 이미 저장돼 있어** 다시 보내면 대화가 이어집니다.
- 검증 오류(남의 기록 404, 마무리됨·10회 초과 409, 빈 내용·1000자 초과 400)는 SSE가 아니라 일반 JSON 오류로 내려 클라이언트가 구분하기 쉽게 했습니다.

### 4) 민감정보 암호화 — 대화는 DB에도 로그에도 평문으로 남기지 않는다
- 케어 대화와 마무리 카드를 **AES-256-GCM으로 암호화**해 저장합니다. 엔티티 필드에 `@Convert(converter = EncryptedStringConverter.class)`만 붙이면 적용되도록 만들어, 새 필드가 생겨도 암호화를 빠뜨리기 어렵게 했습니다.
- **대화 본문은 로그에도 남기지 않습니다.**
- 운영 키는 `APP_CRYPTO_KEY` 환경변수로 필수화하고, 키 분실 시 복호화가 불가능하다는 점을 README에 명시했습니다.

### 5) LLM 공급자 추상화
Upstage Solar Pro 4(HTTP 직접 호출)와 Claude API(SDK)를 `LlmClient` 인터페이스 뒤로 숨기고 `app.llm.provider` 설정으로 고르도록 했습니다. 해커톤 특성상 **API 키 발급·쿼터 문제로 공급자를 급히 바꿔야 할 상황**을 염두에 둔 구성이고, 테스트에서는 `@MockitoBean LlmClient`로 판정을 고정해 **안전 로직을 LLM 없이 검증**할 수 있습니다.

## 🔥 트러블슈팅

**1. 안전 장치가 장애 지점이 되는 딜레마**
*   **문제:** 위험도 분류를 LLM에 의존하면, LLM이 느리거나 죽었을 때 대화 전체가 막힙니다. 그렇다고 실패 시 통과시키면 안전 장치가 무력해집니다.
*   **해결:** 분류기가 **예외를 던지지 않는다**는 계약을 먼저 정하고, 실패·타임아웃(5초) 시 키워드 결과로 폴백하되 **등급 하한을 `CAUTION`으로 고정**했습니다. 호출부는 `llmFailed()`로 폴백 여부를 구분할 수 있습니다.
*   **포인트:** 안전 기능은 "정상 동작"뿐 아니라 **"고장 났을 때 어느 쪽으로 기울 것인가"** 를 함께 설계해야 한다는 것을 배웠습니다.

**2. 스트리밍 중간에 위험 문장이 나오면 이미 늦다**
*   **문제:** SSE로 조각을 흘려보내는 구조에서, 응답 전체를 다 받은 뒤 검사하면 스트리밍의 이점이 사라지고, 조각 단위로 검사하면 문장이 잘려 패턴을 못 잡습니다.
*   **해결:** **문장 단위**로 끊어 검사한 뒤 내보내는 절충안을 택했습니다. 그래도 앞 문장이 이미 나간 뒤 뒷 문장이 걸릴 수 있어, `replace` 이벤트로 **말풍선을 통째로 교체**하는 복구 경로를 프로토콜에 포함시켰습니다.
*   **포인트:** 스트리밍 API는 "성공 경로"만으로 설계하면 되돌릴 방법이 없어, **취소·교체 이벤트를 프로토콜에 미리 넣어야** 한다는 것을 알게 되었습니다.

**3. UTC 환경에서만 깨지던 테스트**
*   **문제:** 기록 관련 테스트가 로컬에서는 통과하는데 특정 환경에서 실패했습니다.
*   **해결:** 테스트가 시각을 주입하는 경로를 **Hibernate 경로로 교체**해, 타임존이 다른 환경에서도 동일하게 동작하도록 수정했습니다.

## 📈 이 프로젝트를 통해 배운 것
- **사흘짜리 해커톤에서도 설계를 생략하지 않을 수 있다**는 것을 확인했습니다. 기획 단계에서 "의학적 진단이 아닌 자기 돌봄 도구"라는 경계를 먼저 못 박았기 때문에, 이후 모든 기술 결정(이중 판정, 안전 가드, 암호화)이 일관되게 따라왔습니다.
- 안전·프라이버시 요구사항을 **기능이 아니라 제약으로 먼저 두면**, `@Convert` 컨버터처럼 "빠뜨리기 어려운 구조"를 만들게 된다는 것을 경험했습니다.
- 외부 LLM처럼 **통제할 수 없는 의존성**은 인터페이스 뒤로 숨기고 교체·목(mock) 가능하게 만들어야 테스트도 운영도 가능해진다는 것을 체감했습니다.
