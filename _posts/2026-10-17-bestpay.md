## 💡 프로젝트 개요
**BestPay**는 실제로 운영 중인 문구점(하이베스트문구 청담점)을 대상으로 한 **온라인 주문 · 매장 픽업 서비스**입니다. 고객이 웹에서 문구를 미리 주문·결제하고 원하는 시간에 매장에서 바로 찾아가며, 사장님은 태블릿/PC 하나로 주문 접수 → 준비 → 픽업 완료까지 처리합니다.

가상의 요구사항이 아니라 **실제 매장의 운영 방식에서 출발한 개인 프로젝트**이고, "1인 개발로 유지보수가 가능한 단순한 구조, 낮은 운영비"를 설계의 제1원칙으로 두었습니다.

| 역할 | 설명 |
| --- | --- |
| 고객 (CUSTOMER) | 상품 탐색, 장바구니, 결제, 주문 현황 |
| 매장 관리자 (ADMIN) | 주문 관리, 상품/재고 관리, 매출 통계 |
| 시스템 관리자 (SUPER_ADMIN) | 설정, 로그, 계정 관리 |

## 🛠 사용 기술
- **Backend:** Java 21, Spring Boot 4.1, Spring Data JPA, **Flyway**, MySQL 8.4
- **Frontend:** Next.js (고객/관리자 웹)
- **인증:** 카카오 OAuth2 로그인 + JWT (access 30분 / refresh 14일, **로테이션**)
- **기타:** Docker Compose(로컬 MySQL), Swagger(local 한정), GitHub Actions CI, 카카오 알림톡

## 📌 도메인에서 출발한 설계

기술 스택보다 **문구점이라는 도메인의 실제 제약**에서 설계를 시작했습니다.

### 1) "재고가 실시간으로 맞지 않는다"
오프라인 판매가 계속 일어나므로 온라인 재고는 본질적으로 **부정확**합니다.
→ 결제 즉시 주문이 확정되는 흐름이 아니라, **사장님이 "수락"해야 확정**되는 구조로 설계했습니다. 품절 상품이 섞인 주문은 **부분 취소(부분 환불)** 가 가능해야 합니다.

### 2) "상품이 수천 SKU다"
하나씩 등록하면 사장님이 지쳐서 서비스를 쓰지 않게 됩니다.
→ **엑셀(CSV) 일괄 등록**과 **바코드 스캔 등록**을 지원 범위에 포함했습니다.

### 3) "등교 전·하교 후에 주문이 몰린다"
→ **픽업 시간 슬롯**을 두고 슬롯당 최대 주문 수를 제한해, 특정 시간대에 감당 못 할 주문이 쌓이지 않도록 했습니다.

### 4) "사장님이 화면을 계속 보고 있지 않는다"
→ 신규 주문 시 **알림음 + 카카오 알림톡**으로 확실하게 전달되도록 설계했습니다.

## 🔐 인증 설계 — 토큰 탈취를 전제로

카카오 OAuth2 인가 코드를 서버가 받아 토큰·회원정보를 조회하고, 첫 로그인이면 자동 가입(`newUser: true`)하는 흐름입니다.

- **Refresh Token 로테이션:** 재발급 시 기존 리프레시 토큰은 폐기합니다.
- **재사용 탐지:** **이미 폐기된 리프레시 토큰이 다시 들어오면 탈취로 간주**하고, 해당 회원의 토큰을 **전부** 폐기합니다.
- **클라이언트가 재시도 가능한 에러 설계:** 401 응답의 `error.code`가 `TOKEN_EXPIRED`면 재발급 후 재요청, 그 외 401은 재로그인하도록 **프론트가 분기할 수 있게** 코드를 구분했습니다.
- **리다이렉트 URI 화이트리스트:** `bestpay.kakao.allowed-redirect-uris`에 등록된 값만 허용해 임의 주소로의 인가 코드 전달을 차단했습니다.
- **권한 분리:** `/api/v1/admin/**`는 ADMIN·SUPER_ADMIN만 접근 가능하며, 상품·픽업슬롯·매장 조회(GET)와 웹훅·헬스체크만 비로그인 허용으로 열어두었습니다.

## 📈 이 프로젝트를 통해 배운 것
- **좋은 설계는 기술이 아니라 도메인 이해에서 나온다**는 것을 체감했습니다. "재고가 안 맞는다"는 현장의 사실 하나가 주문 확정 흐름 전체(수락 기반 확정 · 부분 취소)를 결정했습니다.
- 사용자가 **한 명(사장님)** 인 관리자 화면은, 그 한 명이 실제로 쓸 수 있는지가 전부라는 점에서 기능 수보다 **동선과 알림 설계**가 중요하다는 것을 배웠습니다.
- 인증을 "로그인이 된다"가 아니라 **"토큰이 탈취됐을 때 무엇을 할 것인가"** 에서부터 설계하는 접근을 적용해봤습니다.
