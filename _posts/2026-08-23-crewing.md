## 💡 프로젝트 개요
크루윙(Crewing)은 **항공사 승무원을 대상으로 한 스케줄 관리 앱**입니다. 회사에서 내려오는 개인 비행 스케줄을 업로드하면 캘린더 형태로 자동 정리되고, 항공편의 실시간 출발·도착·지연 상태가 일정에 자동으로 매칭됩니다. 여기에 동료 승무원("크루메이트")과의 스케줄 공유·비교, 스탠바이 위치 추정, 친구 초대, 알림, 캘린더 커스터마이징·외부 캘린더 내보내기, 구독형 프리미엄 상품 "Crewing Plus"까지 갖춘 승무원 전용 생산성 앱입니다.

저는 이 팀의 **백엔드 팀원**으로서 백엔드 개발과 AWS 인프라 운영을 함께 담당하고 있습니다. Spring Boot 3.3(Java 21) 기반 API 서버 개발은 물론, EC2·ALB·RDS 등 운영 인프라 설계와 무중단 배포 파이프라인 구축, 실서비스 데이터 마이그레이션까지 서비스의 전 영역을 엔드투엔드로 책임지고 있습니다.

## 🛠 사용 기술
- **Backend:** Java 21, Spring Boot 3.3, Spring Data JPA, Flyway
- **Database:** MySQL(RDS), Redis
- **Infrastructure:** AWS (EC2, ALB, ACM, Route 53, SES), Docker, GitHub Actions(CI/CD)
- **외부 연동:** Google/Kakao/Apple 소셜 로그인, JWT, AeroDataBox(항공편·공항 데이터), RevenueCat(구독), FCM(푸시 알림), AWS S3(Presigned URL)

## 📌 담당 업무 및 핵심 기여도

### 1) 인증 · 보안
- **소셜 로그인 계정 병합:** `OauthService`에서 이메일로 이미 가입된 계정과 Google/Kakao/Apple 소셜 로그인 계정이 충돌하는 상황을 `findOrCreateUser`/`linkSocialAccount`로 처리. 이미 이메일로 가입된 계정과 소셜 계정이 충돌할 때의 병합 로직을 V1 → V2로 개선하며, 소셜 계정 백필 이슈까지 별도로 대응.
- **Refresh Token 구조 리팩토링:** 토큰 로테이션(`RefreshTokenRotationService`)과 재사용 방지를 위한 Grace 캐시(`RefreshGraceCache`), Opaque 토큰 방식(`OpaqueRefreshTokenService`)을 도입하고, 더 이상 쓰지 않는 레거시 refresh 분기를 제거해 인증 코드베이스를 정리.
- **로그인 시도 제한:** `LoginAttemptService` / `AuthRateLimitService`로 무차별 대입(brute-force) 공격 방어 로직 구현.
- **이메일 인증 보안 강화:** 회원가입·비밀번호 재설정 인증코드 발급/검증 로직(`EmailVerificationService`, `PasswordResetService`)을 점검하고 보강.
- **세션 유지·복구:** 토큰 갱신 도중에도 세션이 끊기지 않도록, 로그아웃 이후에도 상황에 따라 세션을 복구할 수 있도록 처리.
- **인증 공통 규약 정비:** 인증 관련 응답 포맷·에러 코드 등 공통 계약을 정리해 프론트엔드에 전달, 협업 효율을 높임.

### 2) 일정(Schedule) 시스템 v6 리팩토링 & 마이그레이션
- 캘린더 이벤트(`CalendarEvent`) 중심의 새로운 스케줄 구조를 설계하는 **대규모 리팩토링(v6)**을 ERD·API 명세서 정리부터 직접 주도. `FLIGHT·DEADHEAD·BRIEFING·DEBRIEFING·STANDBY·TRAINING·WORK·LAYOVER·OFF·VACATION·PERSONAL` 11개 시스템 카테고리, 동기화 카운터(`calendar_sync_counter`), 삭제 동기화용 tombstone(`calendar_event_tombstones`), 캘린더 스타일 밴드/셀, 커스텀 카테고리, 환경설정, 내보내기 이력(`calendar_export_ledger`) 구조까지 새로 구축.
- **운영 DB 승격 마이그레이션을 2단계로 설계해 진행 중.** 1단계는 오래된 레거시 스키마를 쓰는 운영 DB(`crewing`)의 실데이터를 Flyway로 관리되는 신규 스키마(`crewing_test`, V0~V20)에 맞춰 정합성을 보정하며 이관하는 작업, 2단계는 이관된 `crew_schedule`(레거시)을 신규 `calendar_events` 구조로 변환하는 작업입니다. 두 DB의 스키마 차이를 `mysqldump --no-data`로 직접 대조해 표로 정리하고, 컬럼별 처리 방침(버릴지/보정할지/새로 채번할지)을 하나하나 결정.
- 신규 `calendar_events.id`는 기존 `crew_schedule.id`(bigint)를 그대로 쓸 수 없어 ULID로 신규 채번하고, `schedule_type → category` 매핑 규칙(예: `FLT`+`dh=true` → `DEADHEAD`, `SHOWUP` → `BRIEFING`)은 실제 서비스 코드(`CrewScheduleQueryService`)를 직접 읽어 부작용이 없는지 검증한 뒤 확정.
- 승무원의 근무 스케줄(비행 편명, 스탠바이 등)을 바탕으로 현재 위치를 추정하는 **위치 보간·크루메이트 위치 추정 API**(`CalendarLocationEstimationService`, `StandbyLocation`) 개발.
- 캘린더 일정과 항공편 정보를 연결하는 스케줄-Flight API 구조 정리.

### 3) 항공편 · 공항 데이터 연동
- 외부 항공 데이터 제공사를 **Cirium → AeroDataBox로 전환**.
- 공항의 위경도 좌표를 외부 API로 자동 채워 넣는 **좌표 자동 백필**(`AirportExternalService`) 로직 구현.
- 공항 709건 중 `name_ko`(한글명) 값이 채워진 건 236건(33%)뿐이고 화면에서도 `city_ko`/`country_ko`와 달리 쓰이지 않는다는 걸 실데이터로 확인해 폐기를 결정. 코드 전체의 참조를 `name`으로 교체하고 Flyway 마이그레이션(`V20`)으로 컬럼과 인덱스를 함께 drop.
- 여러 공항 코드를 한 번에 조회하고 없는 데이터는 자동으로 DB에 채워 넣는 **다건 조회 + DB 백필** 구조 개선.
- **공항·항공사 이름 다국어 응답 지원 및 캐시 버그 수정:** 공항 도시명이 DB에 있었지만 어떤 API 응답에도 노출되지 않아, 내장 사전에 없는 공항은 제공사 원문(영문)을 그대로 써서 한 화면 안에서 언어가 섞이는 문제를 발견. 로케일 규칙을 `AirportCityNames`/`AirlineNames` 두 곳에 모아 en은 원문, ko는 한글명이 있으면 그것·없으면 원문으로 내려가도록 통일하고, 다건/단건/검색 응답에 `city`·`cityKo`·`displayCity`를 추가. 배포 후 앱에서 언어를 바꿔도 공항명이 한국어로 남는 재현을 확인해, 30일 캐시 응답에 `Vary: Accept-Language`가 빠져 언어와 무관하게 캐시가 재사용되고 있었음을 찾아내 세 핸들러 모두에 헤더를 추가.
- `FlightLiveController`/`AeroDataBoxLiveFlightService` 기반 **실시간 운항 상태 조회·편명 검색 API** 구현.
- `FlightCachedSearchService`/`AeroDataBoxScheduleSearchService`로 외부 API 호출을 캐싱해 응답 속도 개선 및 API 비용 절감.
- 외부 API 호출량이 쿼터를 초과하지 않도록 방어하는 `AeroDataBoxQuotaGuard` 도입.

### 4) 구독 (Crewing Plus)
- RevenueCat 웹훅(`RevenueCatWebhookController`)을 수신해 구독 상태를 처리하는 백엔드 계약 구현. JWT 인증 대상에서 제외(`SecurityConfig`에 permitAll)하는 대신, RC 콘솔이 지원하는 방식대로 `Authorization` 헤더의 고정 시크릿 값을 컨트롤러 자체에서 직접 비교·검증하도록 설계해 외부 웹훅을 안전하게 수신.
- 구독 관련 스키마 변경(`user_subscriptions` 등)을 포함한 Flyway 마이그레이션 이력 정리.

### 5) 인프라 · 배포 — 무중단 배포 전환 프로젝트
- 기존에는 EC2 1대에서 Docker 컨테이너가 8080으로 떠 있고, 배포 시 GitHub Actions가 SSH로 접속해 컨테이너를 정지→새 이미지 pull→재기동하는 구조였는데, 스프링 부트 콜드 스타트 기준 약 **40초 동안 요청을 처리할 서버가 없어 서비스가 중단**되는 문제가 있었음.
- 이를 해결하기 위해 **신규 EC2 인스턴스(ec2-2)를 부트스트랩**(Docker, 내부 Redis 컨테이너, 앱 컨테이너)해 2대 체제로 확장하고, 단일 인스턴스 nginx 블루/그린 방식과 **ALB + EC2 2대 롤링 방식을 비교 검토**해 후자로 결정.
- ACM 퍼블릭 인증서(도메인 검증), ALB(`crewing-test-alb`, HTTP→HTTPS 리다이렉트), 타겟그룹(`crewing-test-tg`, 8080 포트·헬스체크 기반 라우팅)을 콘솔에서 직접 구성. 작업 도중 기존 인스턴스에 문서화되지 않은 **호스트 nginx+Certbot 구성이 이미 존재**한다는 사실을 SSH로 직접 조사해 발견하고, 보안그룹·리스너 구성 순서를 재설계.
- GitHub Actions 배포 워크플로우를 단일 `deploy` 잡에서 **`deploy-instance-1` → `deploy-instance-2` 순차 잡**(타겟그룹 제외 → 커넥션 드레이닝 20초 → 배포 → 재등록 → 최대 150초 헬스체크 대기 후 다음 인스턴스)으로 재작성. `DescribeTargetHealth`처럼 AWS 정책상 리소스 수준 권한을 지원하지 않는 액션은 `Resource: *`로, `Register/DeregisterTargets`는 타겟그룹 ARN으로 범위를 좁히는 등 IAM 최소 권한 정책도 함께 정비.
- Route 53의 `test.crewing.shop` A 레코드를 인스턴스 IP 직접 지정에서 **ALB 별칭(Alias)으로 전환**하고, 기존 nginx/Certbot 타이머를 정지·비활성화(인증서 파일은 보존)해 레거시 인프라 정리.
- 실제 배포를 트리거하는 동안 `/internal/health`를 **1초 간격으로 500회 이상 직접 호출**해 검증. 전 구간 200 OK만 기록됐고 연결 실패·5xx·타임아웃 없음(응답 시간 대부분 0.04~0.06초, 순간적으로 0.09~0.14초까지 늘어난 구간은 있었으나 실패로 이어지지는 않음) — **다운타임 0건을 실측으로 확인**.
- **S3 버킷 전환 사전 검증:** 운영 승격을 준비하며 기존 S3 버킷을 새 버킷으로 교체해도 되는지 검증. 코드/DB 변경 없이 JVM 시스템 프로퍼티로 버킷명만 오버라이드해 업로드(`S3Service.upload()`)·조회(Presigned GET) 두 경로 모두 실제 요청·응답으로 정상 동작을 확인하고, 버킷 유지/전환 두 옵션의 장단점(마이그레이션 부담, 보안 설정 이월 여부 등)을 비교 문서화.
- **정적 액세스 키 제거 → IAM Role 전환:** 이전 작업에서 미완료로 남아있던 "S3 정적 액세스 키 제거"를 마무리. IAM 정책 리소스 확장과 롤 누락 인스턴스(ec2-2) 발견·조치 후, 실서버 응답의 Presigned URL 서명이 장기 정적 키(`AKIA...`) 대신 임시 세션 자격증명(`ASIA...` + `X-Amz-Security-Token`)으로 발급되는 것을 직접 확인해 EC2 Role 기반 전환을 완료.
- **CloudBeaver 팀 DB 관리 도구 도입:** 팀이 브라우저로 운영/테스트 RDS를 조회할 수 있도록 EC2에 CloudBeaver를 Docker로 추가. 기존 인프라의 "SSH 포트만 최소 허용" 원칙을 그대로 따라 8978 포트는 보안그룹에 열지 않고 SSH 터널로만 접속하도록 설계, anonymous access 차단과 앱 계정과 분리된 최소권한 전용 DB 계정 구성까지 포함한 설정 가이드 문서화.

### 6) 기타
- 클라이언트가 서버를 거치지 않고 S3에 직접 파일을 업로드/다운로드할 수 있는 **S3 Presigned URL**(`S3Service`) 발급 방식 도입.
- FCM 기반 **푸시 알림**(`FirebaseFcmSender`) 처리.
- 패키지 구조 문서, 백엔드 현황 및 개선점, 일정/캘린더 **API 명세서** 등 문서화 작업.
- **기술 부채 정리:** 전체 코드베이스에서 grep으로 호출부가 0건임을 직접 확인한 죽은 코드(미사용 메서드, 주석 처리된 채 방치된 쿼리, 참조 없는 고아 컨트롤러 등)를 식별해 삭제하고, Flyway 도입 이후 더 이상 소스 오브 트루스가 아니게 된 루트의 loose DDL 파일 5개도 함께 정리.

## 🔥 트러블슈팅 및 문제 해결 경험

**1. 인증 메일 발송 실패 — 관찰 가능성 부재부터 짚은 근본 원인 해결**
*   **문제:** 회원가입·비밀번호 재설정 시 인증 메일이 발송되지 않는 장애가 발생.
*   **원인 분석:** 발생한 예외가 로그로 전혀 남지 않아 원인 파악 자체가 불가능한 상태였음. 로깅을 먼저 추가해 관찰 가능성을 확보한 뒤에야, AWS SES가 발신자 아이덴티티뿐 아니라 **Configuration Set 리소스에 대해서도 별도의 IAM 인가를 요구**한다는 사실을 확인.
*   **해결:** 누락된 IAM 정책을 수정해 SES가 정상적으로 메일을 발송하도록 조치.
*   **포인트:** 증상만 고치는 대신 "왜 원인을 못 찾았는가"부터 짚어 로깅 체계를 먼저 보완한 뒤 근본 원인에 도달한 사례.

**2. 무중단 배포 전환 — 추측이 아닌 실측으로 증명**
*   **문제:** 단일 인스턴스 배포 구조에서는 컨테이너 콜드 스타트(약 40초) 동안 요청을 처리할 서버가 없어 배포 때마다 서비스가 중단됨.
*   **해결:** EC2 2대 + ALB 롤링 배포 구조로 전환하면서, 인스턴스를 타겟그룹에서 제외 → 배포 → 재등록 → 헬스체크 통과 확인 후 다음 인스턴스로 넘어가는 방식으로 GitHub Actions 워크플로우를 재작성.
*   **검증:** "무중단"이라는 주장을 코드 리뷰나 추측으로 끝내지 않고, 실제 배포를 트리거하는 동안 헬스체크를 1초 간격으로 **500회 이상 직접 호출**해 전 구간 200 OK, 다운타임 0건을 직접 확인.
*   **부수 소득:** 작업 도중 기존 인스턴스에 문서화되지 않은 호스트 nginx+Certbot 구성이 있다는 사실을 SSH로 직접 조사해 발견, 이를 반영해 배포 계획을 재설계함.

**3. 운영 DB 승격 마이그레이션 — 실데이터 정합성 문제 직접 발굴**
*   **문제:** 오래된 운영 DB(`crewing`)를 Flyway로 관리되는 신규 스키마(`crewing_test`)로 옮기는 과정에서, 스키마 차이는 물론 실데이터 자체의 결함이 다수 발견됨.
*   **사례 1 — 데이터 이상치 탐지 및 복구:** 항공편 스케줄 198,404건 중 `block_minutes`(비행시간)가 도착≤출발이거나 20시간을 초과하는 이상치가 2,245건(1.13%) 존재. 컬럼이 `NOT NULL`이라 단순히 비워둘 수도 없어, 같은 편명+구간의 **정상적인 다른 회차들의 중앙값으로 복구**하는 방식을 설계해 2,020건(90%)을 복구하고, 복구 불가능한 225건(0.11%)만 항공편 상세 없이 캘린더 일정만 생성되도록 처리.
*   **사례 2 — 레이스 컨디션으로 인한 중복 데이터 처리:** 이관 스크립트(`preflight`) 실행 중 이메일이 중복된 계정 3건을 발견. 전부 수십 밀리초 차이로 생성된 행이라 클라이언트 중복 클릭으로 인한 가입 레이스 컨디션으로 판단하고, 연관 테이블(friends/friend_codes/crew_schedule 등 9개)을 전수 확인해 실사용 흔적이 있는 계정만 남기고 제외 대상을 코드로 명시.
*   **사례 3 — 죽은 컬럼 확인 후 정리:** `crew_schedule.flight_type`/`schedule_tag` 컬럼이 운영 데이터 585,270건 전부 `NULL`임을 확인해, 손실 없이 이관 대상에서 제외하기로 결정.
*   **포인트:** "옮기면 되겠지"가 아니라, 두 스키마를 직접 대조하고 실데이터를 전수 검증하며 발견한 문제를 하나씩 근거를 남겨 처리한 경험. (2단계 `crew_schedule → calendar_events` 변환까지 포함해 계획 수립부터 실행까지 진행 중)

**4. Refresh Token 재사용 방지 및 레거시 정리**
*   **문제:** 기존 refresh token 방식은 토큰 탈취 시 재사용을 막을 장치가 부족했고, 레거시 분기가 섞여 있어 유지보수가 어려웠음.
*   **해결:** 토큰 로테이션과 재사용 탐지를 위한 Grace 캐시, Opaque 토큰 방식을 새로 도입해 보안을 강화하고, 더 이상 쓰이지 않는 레거시 refresh 분기를 제거해 코드베이스를 정리.

**5. 로컬 환경에서 실제 푸시 알림이 나가던 버그 — Spring 빈 우선순위의 함정**
*   **문제:** 로컬 개발 환경(`local` 프로필)에서는 로그만 남기고 실제 FCM 푸시는 나가지 않아야 하는데, 코드 점검 중 그렇지 않을 가능성을 발견.
*   **원인 분석:** 더미 구현인 `NoopFcmSender`에 있어야 할 `@Primary`가 주석 처리돼 있어서, 어느 프로필에서든 `@Primary`가 붙은 `FirebaseFcmSender`가 우선적으로 빈으로 선택되고 있었음. 즉 로컬에서도 실제 Firebase FCM API를 호출하도록 배선된 상태였음.
*   **해결:** 두 구현체를 `@Profile("local")` / `@Profile("!local")`로 완전히 상호 배타가 되도록 정리해, 어느 프로필에서도 `FcmSender` 후보가 항상 정확히 하나만 남도록 수정. `@Primary` 기반의 우선순위 방식 자체를 제거해 재발 가능성을 없앰.
*   **포인트:** 여러 구현체가 프로필별로 갈리는 구조에서는 `@Primary`로 우선순위를 주는 것보다 `@Profile`로 상호 배타를 보장하는 편이 더 안전하다는 것을 확인한 사례.

**6. 다국어 응답인데 캐시는 언어를 몰랐던 버그 — Vary 헤더 누락**
*   **문제:** 공항·항공사 이름을 언어별로 다르게 내려주는 기능을 배포했는데, 앱에서 언어를 한국어→영어로 바꿔도 일부 공항명이 계속 한국어로 남는 증상 발견.
*   **원인 분석:** 공항 응답에 30일짜리 `Cache-Control`은 있었지만 `Vary: Accept-Language`가 없어서, 캐시(및 중간 프록시)가 언어와 무관하게 먼저 저장된 응답을 그대로 재사용하고 있었음. 캐시가 히트하는 상태에서는 앱이 요청 자체를 보내지 않아, 서버 로그만으로는 원인을 특정하기 더 어려웠음.
*   **해결:** 다건·단건·검색 세 핸들러 모두에 `Vary: Accept-Language`를 추가해 언어별로 캐시가 분리되도록 수정. 검색 API는 `Cache-Control`은 없지만 ETag 필터가 경로 전체에 적용되므로, 중간 캐시가 언어를 구분하도록 동일하게 처리.
*   **포인트:** 응답 내용이 요청 헤더(언어)에 따라 달라지는 API는 캐시 설정에 `Vary`를 반드시 함께 검토해야 한다는 것을 실제 재현 가능한 버그로 확인한 사례.

## 📈 이 프로젝트를 통해 배운 것
- 기능 개발자에 머무르지 않고, **무중단 배포·실데이터 마이그레이션·장애 대응까지 운영 인프라를 엔드투엔드로 책임지는 경험**을 쌓고 있습니다.
- 문서화되지 않은 실제 인프라 구성이나 데이터 이상치를 스스로 조사해서 발견하고, 그에 맞춰 계획을 수정하는 문제 해결 방식을 익혔습니다.
- "될 것 같다"가 아니라 **실측으로 증명**하는 습관(무중단 배포 500회 반복 검증, 마이그레이션 대상 데이터 전수 확인)을 갖게 되었습니다.
- 장애를 "고쳤다"에서 끝내지 않고, **관찰 가능성(로깅) 부재라는 근본 원인부터 짚고 개선**하는 태도를 배웠습니다.
- AeroDataBox, RevenueCat, SES 등 **외부 API 연동 시 쿼터·보안·장애까지 고려한 설계**를 직접 경험했습니다.
