## 💡 프로젝트 개요
크루윙(Crewing)은 **항공사 승무원을 대상으로 한 스케줄 관리 앱**입니다. 회사에서 내려오는 개인 비행 스케줄을 업로드하면 캘린더 형태로 자동 정리되고, 항공편의 실시간 출발·도착·지연 상태가 일정에 자동으로 매칭됩니다. 여기에 동료 승무원("크루메이트")과의 스케줄 공유·비교, 스탠바이 위치 추정, 친구 초대, 알림, 캘린더 커스터마이징·외부 캘린더 내보내기, 구독형 프리미엄 상품 "Crewing Plus"까지 갖춘 승무원 전용 생산성 앱입니다.

저는 이 팀의 **백엔드 팀원**으로서 백엔드 개발과 AWS 인프라 운영을 함께 담당하고 있습니다. Spring Boot 3.3(Java 21) 기반 API 서버 개발은 물론, EC2·ALB·RDS 등 운영 인프라 설계와 무중단 배포 파이프라인 구축, 실서비스 장애 대응까지 서비스의 전 영역을 엔드투엔드로 책임지고 있습니다.

## 🛠 사용 기술
- **Backend:** Java 21, Spring Boot 3.3, Spring Data JPA, Flyway
- **Database:** MySQL(RDS), Redis
- **Infrastructure:** AWS (EC2, ALB, ACM, Route 53, SES), Docker, GitHub Actions(CI/CD)
- **외부 연동:** Google/Kakao/Apple 소셜 로그인, JWT, AeroDataBox(항공편·공항 데이터), RevenueCat(구독), FCM(푸시 알림), AWS S3(Presigned URL)

## 📌 담당 업무 및 핵심 기여도

### 1) 인증 · 보안
- **소셜 로그인 계정 병합 보안 작업:** 이미 이메일로 가입된 계정과 Google/Kakao/Apple 소셜 로그인 계정이 충돌하는 상황의 병합 처리 로직을 설계·구현. V1 → V2를 거쳐 소셜 계정 백필 이슈까지 별도로 대응하며 반복 개선.
- **Refresh Token 구조 리팩토링:** 토큰 로테이션(`RefreshTokenRotationService`)과 재사용 방지를 위한 Grace 캐시(`RefreshGraceCache`), Opaque 토큰 방식(`OpaqueRefreshTokenService`)을 새로 도입하고, 더 이상 쓰지 않는 레거시 refresh 분기를 제거해 인증 코드베이스를 정리.
- **로그인 시도 제한:** `LoginAttemptService`로 무차별 대입(brute-force) 공격 방어 로직 구현.
- **이메일 인증 보안 강화:** 회원가입·비밀번호 재설정 인증코드 발급/검증 로직을 점검하고 보강.
- **세션 유지·복구:** 토큰 갱신 도중에도 세션이 끊기지 않도록, 로그아웃 이후에도 상황에 따라 세션을 복구할 수 있도록 처리.
- **인증 공통 규약 정비:** 인증 관련 응답 포맷·에러 코드 등 공통 계약을 정리해 프론트엔드에 전달, 협업 효율을 높임.

### 2) 일정(Schedule) 시스템 v6 리팩토링 & 마이그레이션
- 캘린더 이벤트(`CalendarEvent`) 중심의 새로운 스케줄 구조를 설계하는 **대규모 리팩토링(v6)**을 ERD·API 명세서 정리부터 직접 주도. 동기화 카운터, 삭제 동기화용 tombstone, 캘린더 스타일 밴드/셀, 카테고리, 환경설정, 캘린더 내보내기 구조까지 새로 구축.
- 기존 구버전 스케줄 테이블(`crew_schedule`)을 신버전 `calendar_events`로 옮기는 **마이그레이션을 설계·진행**. 과거 버전(v6 비활성화 대비) 참조 정합성까지 고려해 설계.
- 테스트 환경에서 검증한 마이그레이션을 실제 **운영 DB에 승격**하기 위한 계획을 수립하고 진행 중.
- 승무원의 근무 스케줄(비행 편명, 스탠바이 등)을 바탕으로 현재 위치를 추정하는 **위치 보간·크루메이트 위치 추정 API**(`CalendarLocationEstimationService`, `StandbyLocation`) 개발.
- 캘린더 일정과 항공편 정보를 연결하는 스케줄-Flight API 구조 정리.

### 3) 항공편 · 공항 데이터 연동
- 외부 항공 데이터 제공사를 **Cirium → AeroDataBox로 전환**.
- 공항의 위경도 좌표를 외부 API로 자동 채워 넣는 **좌표 자동 백필** 로직 구현.
- 사용하지 않던 `name_ko` 컬럼을 폐기하고 코드 전반의 참조를 `name`으로 교체, Flyway 마이그레이션으로 컬럼을 drop, `city_ko`/`country_ko` 데이터 709건을 정비해 실제 운영 테스트 DB에 반영·검증까지 완료.
- 여러 공항 코드를 한 번에 조회하고 없는 데이터는 자동으로 DB에 채워 넣는 **다건 조회 + DB 백필** 구조 개선.
- `FlightLiveController`/`AeroDataBoxLiveFlightService` 기반 **실시간 운항 상태 조회·편명 검색 API** 구현.
- `FlightCachedSearchService`로 외부 API 호출을 캐싱해 응답 속도 개선 및 API 비용 절감.
- 외부 API 호출량이 쿼터를 초과하지 않도록 방어하는 `AeroDataBoxQuotaGuard` 도입.

### 4) 구독 (Crewing Plus)
- RevenueCat 웹훅(`RevenueCatWebhookController`)을 수신해 구독 상태를 처리하는 백엔드 계약 구현. JWT 인증이 아닌 별도 시크릿 검증 방식으로 외부 웹훅을 안전하게 수신하도록 설계.
- 구독 관련 스키마 변경을 포함한 Flyway 마이그레이션 이력 정리.

### 5) 인프라 · 배포 — 무중단 배포 전환 프로젝트
- 기존 단일 인스턴스 구조에서 **신규 EC2 인스턴스(ec2-2)를 부트스트랩**(Docker, 내부 Redis 컨테이너, 앱 컨테이너)해 2대 체제로 확장.
- 단일 인스턴스 nginx 블루/그린 방식과 **ALB + EC2 2대 롤링 방식을 비교 검토**해 롤링 방식으로 최종 결정.
- 콘솔 작업으로 **ALB + 타겟그룹 + ACM 인증서 구성**(HTTP→HTTPS 리다이렉트, 헬스체크 기반 라우팅). 작업 도중 기존 인스턴스에 문서화되지 않은 호스트 nginx+Certbot 구성이 이미 존재한다는 사실을 SSH로 직접 조사해 발견하고 계획을 재설계.
- GitHub Actions 배포 워크플로우를 단일 배포에서 **인스턴스별 순차 배포(타겟그룹 제외 → 배포 → 재등록 → 헬스체크 통과 확인 후 다음 인스턴스)**로 재작성. IAM 최소 권한 정책도 함께 정비.
- Route 53을 ALB 별칭으로 전환하고 기존 nginx/Certbot 등 레거시 인프라 정리.
- 실제 배포를 트리거하는 동안 헬스체크를 1초 간격으로 **500회 이상 직접 호출해 다운타임이 전혀 없음을 실측 검증**.

### 6) 기타
- 클라이언트가 서버를 거치지 않고 S3에 직접 파일을 업로드/다운로드할 수 있는 **S3 Presigned URL** 발급 방식 도입.
- FCM 기반 **푸시 알림** 처리.
- 패키지 구조 문서, 백엔드 현황 및 개선점, 일정/캘린더 **API 명세서** 등 문서화 작업.

## 🔥 트러블슈팅 및 문제 해결 경험

**1. 인증 메일 발송 실패 — 관찰 가능성 부재부터 짚은 근본 원인 해결**
*   **문제:** 회원가입·비밀번호 재설정 시 인증 메일이 발송되지 않는 장애가 발생.
*   **원인 분석:** 발생한 예외가 로그로 전혀 남지 않아 원인 파악 자체가 불가능한 상태였음. 로깅을 먼저 추가해 관찰 가능성을 확보한 뒤에야, AWS SES가 발신자 아이덴티티뿐 아니라 **Configuration Set 리소스에 대해서도 별도의 IAM 인가를 요구**한다는 사실을 확인.
*   **해결:** 누락된 IAM 정책을 수정해 SES가 정상적으로 메일을 발송하도록 조치.
*   **포인트:** 증상만 고치는 대신 "왜 원인을 못 찾았는가"부터 짚어 로깅 체계를 먼저 보완한 뒤 근본 원인에 도달한 사례.

**2. 무중단 배포 전환 — 추측이 아닌 실측으로 증명**
*   **문제:** 기존 단일 인스턴스 배포 방식은 배포 시점에 서비스가 짧게라도 중단될 수밖에 없는 구조.
*   **해결:** EC2 2대 + ALB 롤링 배포 구조로 전환하면서, 인스턴스를 타겟그룹에서 제외 → 배포 → 재등록 → 헬스체크 통과 확인 후 다음 인스턴스로 넘어가는 방식으로 GitHub Actions 워크플로우를 재작성.
*   **검증:** "무중단"이라는 주장을 코드 리뷰나 추측으로 끝내지 않고, 실제 배포를 트리거하는 동안 헬스체크를 1초 간격으로 500회 이상 직접 호출해 **다운타임 0건을 직접 확인**.
*   **부수 소득:** 작업 도중 기존 인스턴스에 문서화되지 않은 호스트 nginx+Certbot 구성이 있다는 사실을 SSH로 직접 조사해 발견, 이를 반영해 배포 계획을 재설계함.

**3. crew_schedule → calendar_events 대규모 마이그레이션**
*   **문제:** 구버전 스케줄 테이블(`crew_schedule`) 구조로는 캘린더 스타일링, 동기화, 삭제 동기화 등 새로운 요구사항을 수용하기 어려운 상태.
*   **해결:** ERD와 API 명세서부터 새로 정리하는 v6 리팩토링을 설계하고, 동기화 카운터·삭제 동기화용 tombstone 등을 갖춘 `CalendarEvent` 구조로 데이터를 옮기는 마이그레이션을 직접 설계·진행. 과거 버전 비활성화 시점의 참조 정합성까지 고려해 설계했고, 테스트 환경 검증 이후 운영 DB 승격 계획까지 수립.
*   **포인트:** 신규 기능 개발에 그치지 않고, 실데이터가 걸린 마이그레이션을 계획 단계부터 실행까지 주도한 경험.

**4. Refresh Token 재사용 방지 및 레거시 정리**
*   **문제:** 기존 refresh token 방식은 토큰 탈취 시 재사용을 막을 장치가 부족했고, 레거시 분기가 섞여 있어 유지보수가 어려웠음.
*   **해결:** 토큰 로테이션과 재사용 탐지를 위한 Grace 캐시, Opaque 토큰 방식을 새로 도입해 보안을 강화하고, 더 이상 쓰이지 않는 레거시 refresh 분기를 제거해 코드베이스를 정리.

## 📈 이 프로젝트를 통해 배운 것
- 기능 개발자에 머무르지 않고, **무중단 배포·DB 마이그레이션·장애 대응까지 운영 인프라를 엔드투엔드로 책임지는 경험**을 쌓았습니다.
- 문서화되지 않은 실제 인프라 구성을 스스로 조사해서 발견하고, 그에 맞춰 계획을 수정하는 문제 해결 방식을 익혔습니다.
- "될 것 같다"가 아니라 **실측으로 증명**하는 습관(무중단 배포 500회 반복 검증)을 갖게 되었습니다.
- 장애를 "고쳤다"에서 끝내지 않고, **관찰 가능성(로깅) 부재라는 근본 원인부터 짚고 개선**하는 태도를 배웠습니다.
- AeroDataBox, RevenueCat, SES 등 **외부 API 연동 시 쿼터·보안·장애까지 고려한 설계**를 직접 경험했습니다.
