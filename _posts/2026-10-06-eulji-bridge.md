## 💡 프로젝트 개요
**을지브릿지**는 을지대학교 재학생·휴학생·졸업생을 잇는 통합 커뮤니티 플랫폼으로, **멋쟁이사자처럼 을지대학교 14기 단체 프로젝트**입니다.

기존 대학 커뮤니티(에브리타임 등)는 **재학생만을 전제로 설계**되어 있어, 휴학·졸업과 동시에 선후배 관계가 끊깁니다. 을지브릿지는 **졸업생 멘토 ↔ 재학·휴학생**을 직접 연결하는 멘토링을 핵심 기능으로 삼아, 세 신분이 단절 없이 가치를 주고받는 구조를 만드는 것을 목표로 합니다.

> 검증할 단 하나의 가설 — **"졸업한 선배와 재학 중인 후배를, 서비스를 통해 실제로 연결할 수 있는가?"**

- **팀 규모:** 24명 (기획 · 디자인 · 백엔드 · 프론트엔드)
- **MVP 목표:** 2026-12-08
- **제 역할:** 멋쟁이사자처럼 14기 대표로서 **프로젝트 총괄 · 기획 및 운영 문서 체계 수립**

## 📌 담당 업무 — 24명이 같은 그림을 보게 만들기

단체 프로젝트에서 가장 큰 리스크는 기술 난이도가 아니라 **"각자 다른 걸 만들고 있는 상태"** 라고 판단했습니다. 그래서 개발 착수 전에 기획·운영 문서 체계를 먼저 정립하는 데 집중했습니다.

### 1) 문서 정본(Single Source of Truth) 일원화
- 초기에는 Notion과 GitHub에 자료가 분산되어 있었으나, **문서 정본을 GitHub로 단순화**하고 Notion 임포트 자료를 정리했습니다. 코드와 문서가 같은 곳에서 같은 PR 흐름으로 관리되도록 하기 위함입니다.
- `00_문서맵`을 두어 11종의 문서가 서로 어떻게 연결되는지 진입점을 만들었습니다.

### 2) 기획 명세 체계화
- **기능명세를 마스터 → 백엔드 / 프론트엔드 / 디자인**으로 분기시켜, 같은 기능을 각 직군이 자기 언어로 읽을 수 있게 분리했습니다.
- **API 계약 문서**를 별도로 두어 백엔드·프론트엔드가 서로를 기다리지 않고 병렬로 작업할 수 있는 기준점을 만들었습니다.
- 플로우차트로 화면 전환과 상태 변화를 정리했습니다.

### 3) 화면 수 축소 — 범위 관리
- 신분(재학·휴학·졸업)별로 홈 화면을 따로 두던 설계를 **신분별 섹션 1개로 통합**해, **44화면 → 42화면 / 52화면 → 50화면**으로 범위를 줄였습니다.
- MVP 기한이 정해진 프로젝트에서 **범위를 먼저 줄이는 것이 일정 관리의 출발점**이라고 판단했습니다.

### 4) 인원 배정과 일정 관리
- **페어링 배정표**를 만들어 파드(pod) 단위 구성을 명시하고, 백엔드·프론트엔드·디자인 각 직군의 신입 부원(**'아기사자'**) 행에도 담당 영역을 표기해 **누가 무엇을 맡는지 모호한 구간을 없앴습니다.**
- **개인별 작업일정표**를 현재 명세 기준으로 유지하고, 스프린트 번호가 바뀔 때 명세 전반의 표기를 함께 정정했습니다.
- 디자인 파트는 숙련도를 고려해 작업을 배분하고, 부팀장이 미정인 상태는 **"미정"으로 명시**해 추측이 끼어들지 않게 했습니다.
- 신입 부원을 위한 **온보딩 가이드**를 별도로 작성했습니다.

### 5) 역할 경계 정의
- 조직·역할명세에 **팀장의 초기 개발환경 세팅 책임**을 명시했습니다. 24명이 각자 환경을 세팅하면 환경 차이로 인한 문제가 반드시 발생하므로, 팀장이 초기 세팅을 하고 팀원은 clone 후 작업하며 **환경 설정 변경은 팀장이 PR로 반영**하는 흐름을 규칙으로 정했습니다.

## 🛠 프로젝트 기술 스택
팀이 사용하는 스택입니다. (백엔드 구현은 BE 팀장과 팀원이 담당)

- **Backend:** Java 17(LTS), Spring Boot 3, Spring Data JPA, Flyway, MySQL 8.0, Redis, Spring Security(JWT)
- **Frontend:** React, Next.js (반응형 웹 · 백오피스)
- **App:** React Native(Expo) — 확장 단계로 보류
- **Infra:** AWS S3, SES, FCM, GitHub Actions
- **브랜치 전략:** `main`(배포) ← `develop`(통합) ← `feature/{기능ID}-{요약}`

## 📈 이 프로젝트를 통해 배운 것
- 개발자로서의 기여와 **프로젝트를 굴러가게 만드는 기여는 다른 종류의 일**이라는 것을 경험했습니다. 24명 규모에서는 코드 한 줄보다 "이 기능의 담당자가 누구인지 문서에 적혀 있는가"가 일정에 더 큰 영향을 줍니다.
- 기능을 **더하는 결정보다 줄이는 결정**(44→42화면)이 더 어렵고 더 중요하다는 것을 배웠습니다.
- 문서가 여러 곳에 흩어지면 **아무도 최신본을 믿지 않게 된다**는 점에서, 정본을 한 곳으로 모으는 작업의 가치를 확인했습니다.
- 신입 부원이 많은 조직에서는 **모호함 자체가 비용**이라, 미정 사항을 "미정"이라고 쓰는 것조차 명세의 일부라는 것을 알게 되었습니다.
